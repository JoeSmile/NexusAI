# 角色旅程 QA — 分角色验证(2026-08-02 新增)

> 与功能域 QA(01-smoke … 12-demo)互补: 功能域验证"接口正确性",
> 角色旅程验证"这个角色实际干活顺不顺"——揪出脑补出来的、用起来别扭的功能。
> 总纲见 `docs/MANUAL_TEST.md`;旅程发现的别扭点登记到各自 README 的表 + 汇总进 MANUAL_TEST §13。

## 为什么做

Task 30(能力中枢 + 统一前端)的五角色评审指出: 现有 QA 是"端点×角色"权限矩阵,
只验证能不能访问,不验证角色视角的可用性。旅程剧本把验证视角从"测接口"换成"演角色"。

## 四个角色旅程

| 文件 | 角色 | 核心任务 | 重点观察 |
|------|------|----------|----------|
| `01-user.md` | 业务用户 | 用 AI 干活、被拒后申请、反馈 | 引导性/可行动性/来源可溯 |
| `02-tenant-admin.md` | 租户管理员 | 开账号/审批/看成本/配能力 | 租户隔离/审批依据/成本可读 |
| `03-auditor.md` | 审计员 | 查日志/导出/溯源/合规核对 | 还原现场/导出可用/PII 合规 |
| `04-super-admin.md` | 跨租户管理者 | 全局视野/治理/成本/应急 | 总览能力/分摊/故障可见性 |

## 使用方法

1. 后端已起(`make run`),key 齐(见主 README 的 key 约定)
2. 挑一份剧本(建议从 01-user 开始——业务用户视角最容易暴露脑补功能)
3. 按"任务"走,每一步问自己: 这个角色走到这一步,顺不顺?有没有"这功能是给人用的吗"的瞬间?
4. 别扭点记入剧本末尾的"别扭点记录表",三类:
   - **流程断点**: 走到某步无路可走(如 403 后没有申请入口)
   - **信息缺失**: 关键决策看不到数据(如审批时看不到申请人理由)
   - **概念错位**: 功能是技术视角不是用户视角(如"配额"对 admin 是数字,对会计是预算)
5. 实测记录 → 汇总进 `docs/MANUAL_TEST.md` §13 → 作为 Task 30 前端页面的需求输入

## 与 Task 30 的关系

旅程测试发现的别扭点 = 前端要补的页面/交互的需求来源
(例: user 403 后无申请入口 → 前端审批页;admin 看不到 key 最后使用 → last_used_at)。
测出的别扭点合并进 `tasks/30-capability-hub-frontend.md`,再交给 Cursor 实现——先测后写。
